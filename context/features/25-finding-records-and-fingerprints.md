# Feature 25 — Finding Records & Stable Fingerprints

## Goal

Create the durable, tenant-scoped finding identity needed for inline comments,
deduplication, feedback, and later incremental finding reconciliation.

## Depends on

03, 04, 05, 13, 14, 22, 23, 24.

## Scope (do)

- Add the Phase 2 finding enums and table contract to `schemas.md`, then create
  the matching Drizzle migration. This increment contains schema, queries,
  pure mapping, and pipeline wiring only.
- Persist one logical finding row per repository, PR, and deterministic
  fingerprint, but only after Feature 24 returns `confirmed`. Rejected and
  manual-verification candidates never become finding rows. Store confirmed
  structured review output and GitHub comment metadata, but never diff hunks,
  file contents, or prompt content.
- Include tenant and PR ownership directly on each row so every query filters
  by `installation_id` and repository ownership can be checked independently.
- Derive the fingerprint in trusted pure code from normalized finding
  semantics plus a one-way context anchor computed in memory. Do not accept a
  fingerprint generated by the LLM.
- Carry Feature 24's bounded confidence and concrete evidence fields into the
  confirmed finding contract. Confidence from candidate generation is never a
  substitute for independent adjudication.
- Add query operations for upsert-by-fingerprint, list-by-review, list-open-by-
  PR, attach GitHub comment id, and mark terminal status.
- Backfill is not required for historical reviews. Existing review rows remain
  readable with counts and markdown even when they have no finding records.
- Keep existing severity counters on `reviews` as derived rollups for the
  dashboard and daily operational reads.

## Planned finding lifecycle

The schema must support `open`, `resolved`, and `dismissed`. Feature 25 creates
confirmed findings as `open`; Features 28 and 30 own resolution and dismissal
behavior. A dismissed finding cannot silently become open again without a new
fingerprint or an explicit authorized action.

## Security invariants

- All finding reads and writes filter by `installation_id`.
- Finding paths and lines are validated against the processed diff before
  persistence; invalid locations become file-level findings.
- Stored suggestions are review output, not executable instructions.
- Fingerprints contain no reversible source-code fragment.

## Out of scope

Posting inline comments, suggested-change blocks, incremental review,
resolution replies, user feedback, or dashboard management.

## Verification

- Migration and query tests cover tenant isolation, uniqueness, upsert
  idempotency, status transitions, and historical reviews without findings.
- Pure tests prove fingerprint stability for cosmetic wording changes and
  separation for materially different findings.
- Boundary tests reject unknown confidence/lifecycle values and invalid paths
  or line numbers.
- Worker retries do not duplicate finding rows or alter existing GitHub
  comment ids.
