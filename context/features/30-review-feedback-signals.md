# Feature 30 — Review Feedback Signals

## Goal

Let authorized collaborators mark DiffGuard findings as useful, dismissed, or
false positive without introducing general AI chat.

## Depends on

07, 25, 28.

## Scope (do)

- Subscribe to `pull_request_review_comment` events and add a dedicated Zod
  schema for the minimal fields used. The existing webhook route still verifies
  the raw-body HMAC before JSON parsing or schema validation.
- Process only newly created replies to an inline comment whose stored GitHub
  comment id belongs to DiffGuard and to the same installation, repository,
  and PR.
- Support deterministic commands:
  - `@diffguard valid`
  - `@diffguard dismiss: <reason>`
  - `@diffguard false-positive: <reason>`
- Parse commands without an LLM. Unknown text receives no automated action and
  remains available for the final conversational feature.
- Verify the actor's current repository permission through GitHub before
  changing state. `dismiss` and `false-positive` require maintain, write, or
  admin access; `valid` may be recorded from the PR author or a collaborator.
- Add a tenant-scoped feedback record with source comment id, actor login,
  action, bounded reason, finding id, and timestamp. Do not store arbitrary
  thread history.
- Treat false-positive signals as candidates for the offline golden evaluation
  set, not as automatic repository instructions. Promotion requires review and
  a sanitized fixture that contains no persisted source from private repos.
- Apply state changes idempotently. A dismissal moves an open finding to
  `dismissed`; a valid signal does not change lifecycle status.
- Acknowledge accepted commands with one short reply or reaction. Never expose
  internal ids, permission details, prompts, or raw API errors.
- Queue any non-trivial permission check or database work through a signed
  QStash job so the webhook returns quickly.

## Security invariants

- Webhook origin verification does not authorize the commenter; actor
  permission is checked separately at processing time.
- A PR author cannot dismiss a security finding merely by editing webhook
  payload text or replying from an unauthorized account.
- Commands cannot mutate code, configuration, installation access, model
  selection, or findings outside the current PR.
- Bot-authored events and replies generated by DiffGuard are ignored to prevent
  loops.

## Out of scope

Learnings, free-form answers, pause/resume, manual reviews, dashboard
mutations, branch writes, or automatic code changes.

## Verification

- Webhook tests cover invalid signatures, malformed bodies, non-PR comments,
  bot loops, non-DiffGuard parent comments, edits, deletes, and duplicates.
- Authorization tests cover PR author, read, triage, write, maintain, admin,
  removed collaborator, and cross-tenant attempts.
- Command parser tests prove free-form or adversarial text cannot trigger a
  state change.
- End-to-end verification records one valid and one false-positive signal and
  reflects dismissal in the next canonical summary.
